WHAT THE BACKEND DOES TODAY
Verified in crestfall-main on 13 Sep 2026 (the same findings brief 1 recorded, re-read this run).
- The public preview read, GET /v1/creations/:id/preview, hardcodes actorUserId null and the PUBLIC_VIEW access mode (creationPreviewGraph.js), so a private or Internal (UNLISTED) creation answers nothing to anyone, signed in or not. The card route, the landing pages, and the share sheet all stand behind that gate; this is why an Internal creation is blocked in the sheet rather than shared.
- Sign-in has no return path: /login reads no query parameter and /auth/callback always redirects to /studio. A visitor who arrives on a share link, signs in or signs up, lands on the studio home with the page and the sharer lost.
- No referral or attribution code exists anywhere in services-api, the app routes, or the auth callback: no referral table, no cookie, no ref parameter read, no credit on subscription.
- creations.slug is selected and served by every projection and written by nothing; the only slug write in services-api is an engine module instance's own slug.
- The publication review path exists and the frontend already uses it: POST /v1/studio/creations/:id/submit-review with body { reviewType: "PUBLIC" } and the user header, owner only (getOwnedCreation), draft or rejected creations only, official canon locked; it moves the creation to IN_REVIEW, keeps its visibility PRIVATE or UNLISTED, stamps the review payload hash and policy version, and queues certification (certification_status QUEUED). Admin resolution lives at /v1/admin/creation-publication-reviews (list, get, resolve) and the creator reads state at GET /v1/studio/creations/:id/publication-review. The blocked share sheet posts the same call through the frontend route POST /api/creations/[id]/submit-review; no new route was needed, so no CR-078 was filed.
- /v1/profile/me serves no referral fields; the account snapshot's referral.creditedCount is undefined and the counter renders 0.

THE REFERRAL LOOP END TO END
Each step marked FE done, Chassis needed, or the CR that carries it.
1. The share link is built with ref. FE done: every link the package builds ends with ?ref=<sharer username>, the sharer being the signed-in account, never the creator (the creator is the byline). Also the sign-in link the landing page renders: /login?next=<the exact page, ref included>&ref=<username>.
2. The visitor lands and ref is recorded server-side with a 30-day window. Chassis needed, CR-072: read ref on first touch (any page that carries it), persist it against the visitor (cookie or server record), 30 days, last link clicked wins inside the window.
3. The visitor signs in or signs up by any path and returns to the page the link named with ref preserved. Chassis needed, CR-074: honor next on /login and /auth/callback for every sign-in path (email, SSO, any), redirect to the exact same-origin page named, keep ref through the round trip.
4. The account is created with the referral recorded. Chassis needed, CR-072 and CR-074: the referral row is written when the visitor's account is created, pointing at the sharer's account, inside the window.
5. The first subscription on that account credits the sharer once. Chassis needed, CR-072: one credit per referred account, on that account's first subscription, last link clicked wins inside the window; the bonus amount is directional pending research and no coin number exists in code or copy.
6. referral.creditedCount is served on the account snapshot. Chassis needed, CR-073: /v1/profile/me carries referral: { creditedCount, pendingCount }.
7. The profile counter renders it. FE done: the Referral bonus row on /studio/v2/account reads referral.creditedCount from the snapshot, 0 until served, never hidden, no coin number, no policy link until a referral policy page exists.

GAPS
One line per gap, in the shape: what the FE calls, the inputs, the response the FE expects, what is unverified. Numbered by CR.
- CR-072, referral attribution from share links. Call: none yet; the FE sends ref on every share link and on the sign-in link. Inputs: ref=<sharer username> on the landing URL, the image destination, and /login. Response: a server-side first-touch record with a 30-day window, a referral row when the visitor creates an account, one credit to the sharer on that account's first subscription, last link clicked wins inside the window. Unverified: where the record lives (cookie, session, table), and whether the sharer must still hold an account at credit time.
- CR-073, the referral counter on the account snapshot. Call: GET /api/profile/me, forwarded to GET /v1/profile/me (the existing account read). Inputs: none. Response: referral: { creditedCount: integer, pendingCount: integer } on the profile payload, or as a top-level data.referral; the frontend client reads either. Unverified: nothing; the counter folds a missing field to 0 today.
- CR-074, sign-in return path and ref carry-through. Call: /login?next=<same-origin path>&ref=<username>, then /auth/callback. Inputs: next (the exact page, ref included), ref. Response: after any sign-in or sign-up path the visitor lands on next, both for the playable landing (/c, /story, /adventure) and the image destination (/studio/creations/:id?image=<outputId>, or the sharer's profile), and ref is persisted into the new account for CR-072. Unverified: whether the callback can carry state through the SSO round trip without a server-side handoff record.
- CR-075, Internal creations readable by signed-in recipients. Call: GET /v1/creations/:id/preview (and the routes the card and landing pages read through it). Inputs: the creation id plus the signed-in actor. Response: DIRECT_LINK_VIEW with the actor (or the existing direct-access route proxied), so an Internal link opens for a signed-in player. Unverified: whether Brian wants Internal sharing back at all now that sharing is public only; until he rules, the sheet blocks Internal and this CR stays open for the landing family and the card only.
- CR-076, server-written creation slug. Call: the publish and approval paths that move a creation to PUBLIC. Inputs: the title. Response: creations.slug written at publish (lowercase, hyphenated, bounded), served on every projection as today; the landing routes redirect a stale slug to the canonical one and the frontend stops deriving it. Unverified: uniqueness policy when two creations share a title.
- CR-077, named image selection on the public creation page. Frontend work, not Chassis: app/studio/creations/[id]/page.js reads no image parameter today, so an image share lands on the page without selection and without an Open Graph image; the same later brief that opens the named image adds generateMetadata there with the shared image's medium derivative and the card route otherwise. Nothing for Nick unless the page needs a served field to select by output id.
- CR-078, not filed. Brief follow-up 1 reserved this number for a publication review call the frontend could not reach; the call exists (POST /v1/studio/creations/:id/submit-review, above) and the blocked sheet posts it, so nothing was filed and the number stays free for the next lane.
- Open question, the affiliate program. The community affiliate program and the referral credit could both claim one sign-up; the frontend takes no position. Needed from Nick: which record wins when a visitor arrives with ref and an affiliate code (or an affiliate cookie) in the same window, and whether one sign-up may ever credit both. Until answered, CR-072 credits nothing.
